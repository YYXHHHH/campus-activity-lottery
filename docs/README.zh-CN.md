## 三、推荐阅读顺序

1. **了解项目**：项目开发计划 → 需求规格说明书
2. **理解方案**：概要设计说明书 → 详细设计说明书 → 数据库设计说明书 → 接口设计说明书
3. **核查实现**：实现说明
4. **验证质量**：软件质量保证计划 → 测试计划 → 测试报告 → 验收报告
5. **上线使用**：部署运行手册 → 用户操作手册
6. **复盘结项**：项目总结报告

## 四、文档来源与整理规则

- **需求规格说明书** ← 《需求与设计文档》§1~§6、§12.2、§15.1~§15.2；
- **概要设计说明书** ← 《开发文档》§1~§2 与《需求与设计文档》§7、§10；
- **详细设计说明书** ← 《开发文档》§3、§5~§7 与附录 A/B；
- **数据库设计说明书** ← 《开发文档》§4 与《需求与设计文档》§8.3、§8.5；
- **接口设计说明书** ← 开发完成后的接口清单（重命名为规范文档名）；
- **测试计划** ← 《开发文档》§10、附录 D 与《需求与设计文档》§12.1、§12.3；
- **验收报告** ← 开发完成后的手工验收清单（重命名为规范文档名）；
- **项目开发计划 / 质量保证计划 / 配置管理计划** ← 《需求与设计文档》§6、§13、§14，《开发文档》§6、§7、§9、§10，以及项目实际工程实践；
- **项目总结报告** ← 《实现说明》§7、《测试报告》、《验收报告》与过程记录。

> 拆分文档的章节编号沿用来源文档，便于与正式原件交叉检索。

## 五、归档与构建

- `99-archive/`：仅保留开发当日过程记录，供追溯；其余原始材料已并入各阶段文档或移除。
- `scripts/`：文档构建与校验脚本，位于 docs/ 之外，保持文档目录只含文档。
- 生成的 `.docx` 已被 `.gitignore` 忽略，仓库保持轻量。

## 六、维护约定

- 每篇文档只描述其所属阶段的内容；跨阶段信息通过引用而非复制传递。
- 以 Markdown 为唯一源；需要 Word 版时运行 `scripts/md_to_docx.py`。
- Word 目录为域：在 Word / WPS 中按 `updateFields` 自动更新，或按 F9 手动更新。
- 需求变更先改《需求规格说明书》，再同步设计、数据库、接口与测试文档。
- 归档目录只增不改，用于追溯整理前的原始材料。
